# Sprint 2.1 evaluation limits

The original expanded benchmark had 25 answerable queries and five no-answer queries. Each answerable query had one relevant record, so precision@5 could not exceed 1/5 = 0.20. Its 0.50 precision gate was mathematically invalid, regardless of ranking quality.

The revised 30-query diagnostic selected 20 answerable and ten no-answer queries. It retained six singly labeled repository facts and therefore still had a 0.20 precision@5 ceiling. That fixture remains an interim historical diagnostic.

The reviewed held-out fixture uses 20 distinct repository investigations, ten no-answer questions, and 64 distinct real TypeScript source/test files as its retrieval corpus. The 20 answerable questions cite 66 relevant query/file pairs, so maximum aggregate precision@5 is 66/100 = 0.66 and the 0.50 gate is achievable. A separate eight-query development set selected a lexical coverage threshold of 0.6 from a predeclared 0.2 to 0.8 grid: 4/4 answerable candidate coverage and 0/4 no-answer candidate returns. This tiny set does not establish semantic answerability.

On the held-out run (Windows, Node 22.14.0), raw retrieval measured precision@5 0.44, recall@5 0.683, 10/10 no-answer queries with a raw candidate, 100% answerable coverage, a 53.3% incorrect-first-result rate, and zero forgotten-record leakage. The grounded candidate operation measured precision@5 0.09, recall@5 0.133, 0/10 no-answer candidate returns, 60% answerable candidate coverage, and a 10% unsupported-candidate rate. Its `canAssert` field is always false, so these candidate metrics do not establish answer accuracy. The held-out acceptance gates fail.

Precision@5 divides retrieved relevant records by five per answerable query, including when fewer than five records are returned. Recall@5 divides relevant records returned by the one labeled relevant record per answerable query. Answerable coverage is the fraction of answerable queries with any result. Incorrect-answer rate is the fraction of all queries whose first result is not the labeled relevant record, or whose no-answer query returns any result. No-answer false-positive rate is the fraction of no-answer queries with any result. A conflict is not represented in this fixture; any result on a future conflict case must be assessed against explicit conflict labels rather than assumed correct. Stale leakage counts returns of the superseded fixture record; it does not validate source-file freshness.

For the 64-source held-out timing, each of 30 queries is warmed once, followed by five measured grounded-search calls. p50/p95 are nearest-rank percentiles across 150 calls: p50 49.77 ms and p95 60.65 ms. The corpus contained the real source/test files plus one forgotten sentinel record and no synthetic distractors. The separate historical baseline remains 500/10,000 records with its original seven queries. Neither fixture establishes quality on real user tasks.

The held-out command intentionally reports `passed: false` until retrieval, abstention, forgotten-memory, stale-source and latency gates pass. Stale-source leakage was not measured in this fixture. Conflicts are caller-declared in the experimental grounded API; automatic contradiction detection and semantic answerability remain unverified. The old expanded command does not determine held-out acceptance.
